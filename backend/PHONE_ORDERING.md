# Phone Ordering Recording Path

Shopkeepers place calls with the device `tel:` dialer. e-Setu does not automatically record ordinary cellular calls. On this PWA there is no native Android `InCallService`; Android's `CallScreeningService` exposes call metadata, not media, and the `VOICE_CALL`, `VOICE_UPLINK`, and `VOICE_DOWNLINK` audio sources require `CAPTURE_AUDIO_OUTPUT`, a permission reserved for system components. A microphone-only capture would not reliably contain both sides, so it is intentionally not presented as call recording.

Free manual path: return to `कॉल`, open the correct recent supplier call, select `रिकॉर्डिंग जोड़ें`, and choose a WAV, MP3, or M4A call recording. The server validates the size and audio decoding, checks the SHA-256 digest, associates the file with that existing call and its supplier/customer data, and hands it to the existing STT -> extraction -> supplier review pipeline. Unknown customers remain unknown until explicitly identified. A recording or draft already attached to the call is never silently replaced.

Suppliers can choose a shopkeeper, launch a normal device `tel:` call, and attach its recording to that logged call. A supplier may also send a targeted 10-minute wait notice to a known shopkeeper. The expiry and supplier/call association are stored on the shopkeeper account, the notice uses the existing OneSignal subscription when available, the Calling screen shows a decreasing countdown, and the call-log API atomically rejects new shopkeeper app calls until the wait expires. A supplier-initiated call remains available during that window. This only blocks calls started through e-Setu; the web app cannot prevent someone from dialing manually outside it.

Audio is stored privately, streamed only through authenticated endpoints, limited to 64 MB by default, and removed after the configured retention period (30 days by default). Storage has two backends behind one interface, chosen by `PILOT_AUDIO_BACKEND` (`auto` by default): in production, with `CLOUD_NAME`/`API_KEY`/`API_SECRET` set, recordings go to durable Cloudinary storage; otherwise they go to the local directory. Falling back to local disk in production is ephemeral and is reported as a warning at startup, because a redeploy would otherwise silently lose the only copy of a call.

Durable recordings are uploaded as `esetu/phone-calls` assets with `type: authenticated`, so they have no public delivery URL and cannot be listed or searched; the asset name is built from nothing a caller supplies, so it carries no supplier, customer, or phone number; and the original format is preserved rather than re-encoded. The backend is the only reader, using a signed URL requested after the caller's ownership of the call is verified. Transcription still works on a file path, so a durable recording is fetched into a short-lived working copy under `PILOT_AUDIO_DIR/tmp` for the length of the call and removed afterwards. Nothing on the failure path deletes the stored recording, which is what makes a retry after a redeploy work: the retry re-reads the same asset rather than asking the supplier for the file again.

Recordings taken before durable storage existed keep working unchanged, because a document with only `audio.fileName` and no `storage` is read as a local recording. To move those across, run `npm run backfill:audio` for a dry run and `npm run backfill:audio -- --apply` to perform it; the script is idempotent, skips anything already holding a `publicId`, and leaves the original files on disk. Deployments with ephemeral disks can still expect a local-only recording to disappear at restart until it is backfilled.

After retention cleanup, file and digest references are cleared so an upload can be retried only when no transcript/review pilot already exists for that call. The same period, `PILOT_AUDIO_RETENTION_DAYS` and 30 days by default, expires durable recordings: a recording is aged by `storedAt` where a local file is aged by its mtime, and the asset is deleted only once no real Order depends on the call, no pipeline stage is reading it, and no order is being created against it. A recording that an order was built from is kept, because the supplier may need to listen back to the call behind it. The reference to the asset is cleared only after the delete succeeds, so a failed or interrupted sweep simply tries again on the next run and never loses track of where a recording lives.

A real Android implementation would require a separate native dialer app selected as the user's default phone app plus device/OEM and policy validation. It is not a capability this browser/PWA can add. The existing STT/review and protected confirmed-draft-to-Order bridge remain the sole order pipeline.

Ordering is one tap, not two, but never zero. The supplier still reads every line of the extracted draft and resolves anything flagged before confirming; the confirm tap sends `createOrder: true`, and the bridge then does all the writing. Nothing the AI produced is trusted at that point: the bridge re-resolves each product, variant, availability and price against the live catalog, refuses an unidentified customer, and merges into the customer's existing pending order under the same per-user lock the cart uses. The order is created by the bridge alone, so the duplicate guard, the claim timeout and the audit trail behave identically whether the supplier orders from the review screen or from the retry button. If the bridge refuses, the confirmed draft is kept and the exact reason is shown, and confirming again retries the order rather than short-circuiting. A draft confirmed earlier and left unordered stays visible with a retry, and a draft already carrying an order says so instead of offering to create a second one.
